# Dimensional Battlefield Implementation Plan

> **For agentic workers:** Use subagent-driven-development for task implementation with scoped reviews. The root integrates and verifies. User-approved direction and explicit implementation request supply authorization; do not ask again for already chosen references/engine/depth/cards/motion/device targets.

**Goal:** Replace the flat match screen with a real 3D, cinematic four-arena battlefield while preserving legal gameplay and accessible controls.

**Architecture:** Three renders geometry/card planes and projects semantic DOM anchors using the same camera. React remains interaction owner; the existing public-view event reducer and GSAP presentation controller remain the only event clock. Match-only CSS overlays compact HUD/hand/inspector without moving targets.

**Tech Stack:** Next/React, Three.js 0.186.1, @types/three 0.186.0, existing GSAP and TypeScript.

**Spec:** `docs/design/arena-3d-contract.md`.

## Global constraints

- UI only. No API/DB/engine/catalog/auth/audio edits; preserve all user-owned dirty files, including App/layout/Settings/shell.css and unrelated docs/tests.
- Existing main checkout is user-authorized; no new branch/worktree. Root handles eventual scoped commits/push only after verification. No deployment until the UI integration is verified.
- Preserve the five lanes, public state, target serialization, exact command intent, and immutable content versions.
- Preserve original Pen/source art. Current card design and gem geometry remain. The new table is an approved design extension.
- Only one active Three renderer; no concurrent Pixi renderer. GSAP owns visual choreography, reduced motion and lifecycle cleanup are mandatory.

## Review focus

1. Both player factions: near/far rows and target projection cannot swap identities or lane order.
2. Rapid events, skip, reconnect, reduced motion and quality changes: no camera drift, orphan resources or stale presented state.
3. Small/rotated screens and opening inspector: the board must remain actionable and phase controls reachable.
4. Missing art/WebGL loss: semantic current state and actions must survive, and retry must mount exactly one canvas.
5. Hidden locations/event assets: only public definitions may appear; camera effects must not leak secret state or send commands.

### Task 1: Three scene, four environments and projected controls

**Files:** Create `apps/web/src/features/match/rendering/three/{layout,environment,card-texture,scene}.ts`, optionally focused helpers there; `rendering/scene-state.ts`; `apps/web/tests/arena-3d.test.ts`. Modify `BattleScene.tsx`, `rendering/scene.ts`, `apps/web/package.json`, `pnpm-lock.yaml`. No MatchScreen/Board/CSS ownership in this task.

**Interfaces:**

- `createThreeBattleScene(canvas: HTMLCanvasElement, catalog: PublicCatalog, options: { quality: 'low' | 'high'; reducedMotion: () => boolean; arenaKey?: string; onFailure?: () => void }): BattleScene` preserves existing `ready/applyView/getView/subscribe/commit/present/clearEffects/setPaused/dispose` behavior. BattleScene retains the initial arenaKey in a ref so quality changes/retries do not change it.
- Extract/re-export existing `applyVisibleEvent` reducer and BattleScene/Cue types into `scene-state.ts` without behavior changes; old scene exports remain compatible.
- Canvas layer is positioned/sized to `.board` inside nearest `[data-battle-root]`; renderer sets `data-renderer="three"`, `data-arena-3d="ready"` on root only after successful render, removes on failure/dispose. CSS can restore DOM board otherwise.
- Projection updates `[data-slot-lane][data-slot-side]`, `[data-unit-id]`, `[data-lane-id]`, `[data-terrain-lane]` inside `.board`. CSS variables `--project-x`, `--project-y`, `--project-width`, `--project-height` use px relative to board. Set `data-projected="true"`; optional `--project-clip` holds a polygon for exact hit geometry. Unit and empty slot use their real near/far row; lane-target uses the near empty tile; terrain uses central band. Dispose clears owned attributes/styles. Existing Board already supplies these hooks except unit side/lane can be inferred by instance ID.
- Canvas must have no pointer interception. DOM owns all targets. DOM stats remain upright below the projected card. Card texture uses current public unit stats and existing frame/gems. The scene observes DOM updates and selection/focus without issuing commands.
